# 动态管理与误判过期动态修正设计

## 目标

将“过期动态重新识别”放入动态管理页面，处理历史数据中被错误识别为过期、但实际没有完成抽奖参与操作的动态。

## 页面结构

动态管理页面包含两个可折叠列表：

1. 失败动态
2. 过期/疑似误判动态

列表默认保持简洁，只显示标题、数量和操作按钮。展开后显示动态明细。

每条动态显示：

- 动态链接
- UP 主 ID
- 入库时间：`insert_time`
- 动态发布时间：`publish_time`
- 开奖时间：`lottery_time`
- 当前状态

失败动态保留现有的单条“页面丢失”操作。过期动态提供单条“重新识别”操作。

## 重新识别流程

过期动态重新识别只对 B 站执行读取操作：

- 打开动态详细页；
- 读取动态发布时间；
- 读取开奖接口信息；
- 读取正文并解析开奖时间；
- 读取 UP 信息；
- 不执行关注、点赞、评论、预约、转发、删除或取关。

重新识别按 `t_draw_dynamic.status='2'` 查询，排序规则为：

```sql
ORDER BY insert_time ASC, dynamic_id ASC
```

总按钮每次最多处理 100 条，每条之间随机等待 20～30 秒。单条操作使用相同的识别逻辑。

## 状态处理

重新识别成功后：

- 如果实际已过开奖时间，保持 `status='2'`；
- 如果实际尚未开奖，将动态恢复为待转发状态 `status='0'`；
- 同时更新 `publish_time`、`lottery_time`、`lottery_source`；
- 清除或更新旧的错误备注。

恢复为 `status='0'` 后，动态自动进入正常转发队列。后续正常任务负责执行关注、点赞、评论和转发，并按照已有的 `dynamic_id` 去重逻辑避免重复参与。

重新识别失败时：

- 保留原状态；
- 不进入待转发队列；
- 写入运行日志；
- 在本轮结果中记录失败数量。

## 后端接口

沿用现有后台任务状态结构，新增：

- `GET /api/tasks/manual-status`
  - 返回总重新识别任务状态；
- `POST /api/tasks/manual/reidentify_expired`
  - 后台启动最多 100 条重新识别；
- 动态管理列表接口扩展或新增过期动态列表；
- 单条重新识别接口使用同一识别服务，避免页面逻辑复制。

总任务与单条任务需要互斥，避免同一动态被同时重新识别。收集/转发任务和重新识别任务也应复用现有任务锁，避免 Selenium 会话并发冲突。

## 数据和安全边界

- 不新增数据库表；
- 不改变已有表结构；
- 不删除任何历史动态；
- 不执行 B 站写操作；
- 只有动态重新识别确认未开奖后，才将本地状态改为 `status='0'`，等待正常转发任务执行；
- 清理任务仍使用现有“明确开奖时间 +10 天”的规则。

## 验证

验证范围：

- 语法编译和接口路由；
- 动态管理页面列表可展开/收起；
- 每条记录显示 `insert_time`、`publish_time`、`lottery_time`；
- 总重新识别按钮每次最多处理 100 条；
- 重新识别之间等待 20～30 秒；
- 未开奖动态恢复为 `status='0'`；
- 失败和确认过期动态不改变错误状态；
- 重新识别流程不调用 B 站写操作；
- 恢复后的动态可被正常待转发查询获取。
